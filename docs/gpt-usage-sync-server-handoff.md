# GPT 用量同步服务端实施交接

GPT 用量同步中心服务支持多台机器上传、下载用量明细和设备信息。
服务端负责认证、验证、持久化与增量分发；
MAA 客户端负责采集日志、谱系去重、设备筛选、费用计算和界面展示。

协议版本固定为 v1，与 MAA 应用版本独立。本文包含实施要求、完整报文、
存储建议和验收场景，可直接交给负责服务端的 agent。

已按 2026-10-12 的服务端交付说明更新账户、错误码及分页限制。
服务端已有账户管理和审计后台，公开同步接口仍为以下三个 v1 接口。

请先阅读服务端目标仓库的协作规则，然后按本文维护三个 v1 接口、持久存储、
共享密钥认证、原子批量写入和固定上界的分页下载，并完成隔离环境中的契约测试。
语言、框架和数据库遵循目标仓库约定；本文的逻辑表结构可按所选数据库调整。
不要修改 MAA 客户端来适配另一套接口。

交付源码、数据库迁移、无真实密钥的配置示例、测试和启动说明。
本客户端仓库不部署正式服务器、不提供注册账号体系；账户管理在服务端后台完成。

## 业务边界

- 只同步会话标识、分叉关系、原始模型名、UTC 时间、Token 明细和来源设备。
- 不接收对话正文、工具参数、文件路径、采集目录、GPT 凭据、价格或费用。
- 不调用 OpenAI 接口，不做会话恢复，不提供注册、账号登录或服务端删除接口。
- 首次同步上传全部本机已采集历史，此后只上传未确认的记录。
  下载缓存不会重新作为本机采集数据上传。
- 没有本机日志的机器也能下载查看。删除 Codex 原日志不删除已采集历史。
- 同一用量由两台设备采集时，服务端必须保留两条来源关系。
  客户端汇总时只计一次；各设备分项不保证能够直接相加。
- 按设备清理只是某台 MAA 的本地缓存操作。后续下载可以恢复，
  不向服务器发送删除请求或全局删除标记。

## 连接与认证

基础地址由用户填写，默认空；同步密钥也默认空。客户端只在配置完整后联网。
基础地址可以带路径前缀，例如配置 `https://sync.example.com/maa` 时，
接口是 `https://sync.example.com/maa/api/v1/codex-usage/handshake`。

客户端只接受 HTTPS，并拒绝 HTTP 重定向。可以由反向代理终止 TLS，
但用户填写的入口必须直接返回协议响应，不能重定向到登录页或另一条路径。
原生 Rust 客户端发送请求，不依赖浏览器 Cookie、CORS 或账号登录流程。

每个请求携带以下请求头；push 还携带 `Content-Type: application/json`。

```http
Authorization: Bearer <共享同步密钥>
Accept: application/json
```

管理员在“MAA同步 → 账户管理”创建账户，同一账户的所有机器使用同一个密钥。
每个账户对应一个稳定空间和一个当前有效密钥；不同机器各自持有独立设备 ID。
密钥由服务端安全随机生成，明文只在创建或重置时返回一次，数据库保存摘要。
启动种子配置仅用于导入已分发密钥，不覆盖已有账户状态。

共享密钥是同步空间的读写凭据，
不是 GPT 登录凭据。由密钥决定授权空间，再核对请求中的 `spaceId`；
不能仅信任客户端传入的空间标识。不同空间的设备、记录和游标严格隔离。

密钥以受保护的配置或密钥摘要管理，不提交真实密钥。
停用账户返回 403，启用后沿用原空间；重置密钥后旧密钥返回 401。
启停、换钥均不清空历史、不改变 epoch 或游标。客户端换钥后使用独立本地缓存，
重新确认本机历史并下载；服务端幂等保存，不能要求复用旧密钥对应的确认状态。
Authorization、密钥、游标和请求正文不得进入访问日志、错误日志或追踪系统。
v1 没有设备级登录凭据，`deviceId` 表示采集来源，不能视为独立认证身份。
测试连接仅执行 handshake，不登记设备；首次成功 push（含空记录）登记设备。
handshake 和 changes 不携带 deviceId，不得为审计增加未知字段或查询参数。

每个空间有持久的 `epoch`，表示服务端数据代次。正常重启不改变它；
数据恢复、重建或回滚导致旧上传确认或游标不再可靠时必须更换。
`spaceId` 和 `epoch` 都是 1～256 UTF-8 字节且不含控制字符的字符串。

所有成功响应必须是 HTTP 200 和 JSON。201、202、204、重定向及 HTML 错误页
均不能作为成功响应。客户端单次请求超时为 40 秒，不支持异步提交任务票据。

## 数据格式与内容哈希

所有字段使用 camelCase，必填的可空字段仍须输出，值为空时写 `null`。
JSON 只传非负十进制整数 Token 和时间，不接受数值字符串、小数、指数或负零。

| 数据 | 限制 |
| --- | --- |
| `deviceId` | 32 个小写十六进制字符，由客户端随机生成并持久保存 |
| 设备 `name` | 1～128 UTF-8 字节，不能全为空白或包含控制字符 |
| `sessionId`、非空父 ID、`model` | 1～512 UTF-8 字节，不能全为空白或包含控制字符 |
| `createdAt`、`timestampMs` | `null` 或 `0..8210266876799999` 的 UTC Unix 毫秒整数 |
| Token 及累计计数器元素 | 整数，范围 `0..9007199254740991` |
| `totalUsage` | `null` 或恰好包含 5 个 Token 整数的数组 |
| `occurrence` | 整数，范围 `0..4294967295`；累计计数器非空时必须为 0 |
| `recordId` | 64 个小写十六进制字符，必须与内容哈希一致 |
| 单次 JSON | 请求、响应分别最多 1048576 字节，按未压缩 UTF-8 JSON 计数 |
| 每批或每页 | 上传最多 500 条；下载记录来源与设备变更合计不超过 limit（默认 500） |

长度按 UTF-8 字节计算，不能只依赖 JSON Schema 的字符数限制。
记录字符串校验通过后原样保存，不 trim、不改模型大小写、不做 Unicode 归一化。
实际比较和唯一约束要区分大小写，避免数据库排序规则合并不同会话标识。

会话记录如下。没有用量的会话也必须保存，以连接跨机器的分叉关系。

```json
{
  "kind": "session",
  "sessionId": "thread-1",
  "forkedFromId": null,
  "createdAt": 1791504000000
}
```

用量记录如下。

```json
{
  "kind": "usage",
  "sessionId": "thread-1",
  "timestampMs": 1791504000000,
  "model": "gpt-example",
  "inputTokens": 80,
  "cacheReadTokens": 20,
  "outputTokens": 10,
  "totalUsage": [100, 20, 10, 0, 110],
  "occurrence": 0
}
```

`inputTokens` 已排除缓存命中部分。`outputTokens` 已包含推理输出，
服务端不能再加推理 Token。`totalUsage` 保留日志原始累计值，顺序固定为
`[input_tokens,cached_input_tokens,output_tokens,reasoning_output_tokens,total_tokens]`。
不能用上述明细字段重算或修正这五个累计值。

无累计计数器时，`occurrence` 区分日志里内容相同但实际重复发生的事件。
无原始会话 ID 的旧日志使用 `legacy:<deviceId>:<随机文件ID>`，
仅保证本机幂等，不能保证跨机器识别其复制件。不要去掉这一标识中的设备部分。

### 哈希算法

先按下列固定字段顺序构建数组，再编码成紧凑 JSON 的 UTF-8 字节，
计算 SHA-256，输出小写十六进制。哈希不包括外层包装或来源设备 ID。

```text
[1,"session",sessionId,forkedFromId,createdAt]
[1,"usage",sessionId,timestampMs,model,inputTokens,cacheReadTokens,outputTokens,totalUsage,occurrence]
```

编码不含 BOM、空格或末尾换行；整数使用十进制，不转义 `/` 或非 ASCII 字符，
双引号和反斜杠使用标准 JSON 转义，可空值使用 `null`。
不要对原始 HTTP 请求字节、record 对象键排序后的 JSON 或数据库 JSON 输出做哈希。

下面每个数组是一行完整的哈希输入，下一行是预期结果。

```text
[1,"session","thread-1",null,1791504000000]
fd3127c801e7b05afb5d900c6f091806b8e01e5f64a5b3ce70fe22fba89d5f67

[1,"usage","thread-1",1791504000000,"gpt-example",80,20,10,[100,20,10,0,110],0]
ba432543859b5784bca4c5293c5c41afdb1ba4be71677028f0d664854620df5f

[1,"usage","会话/\"1",null,"模型\\A",1,0,0,null,2]
8301484be9dc31c5b241658355f3e68a5efde92ac2e716a158783cf1974dcb22
```

`session`、`usage`、设备对象、`WireRecord`、`RemoteRecord` 拒绝未知字段。
push 请求遵循 OpenAPI 的封闭结构；握手、上传确认、分页响应的最外层对象
允许增加不影响现有语义的字段。不要给每条 record 添加服务端时间或数据库主键。

## 三个 v1 接口

### GET handshake

路径为 `/api/v1/codex-usage/handshake`。验证 Bearer 密钥，返回所属空间和代次。
无必填查询参数，不要求设备注册，也不要求请求携带协议版本头。
客户端通过响应中的 `protocolVersion` 判断兼容性。

```json
{
  "protocolVersion": 1,
  "spaceId": "space-example",
  "epoch": "epoch-example"
}
```

MAA 的「测试连接」只调用这个接口，不上传用量或设备信息。

### POST push

路径为 `/api/v1/codex-usage/push`，请求示例：

```json
{
  "protocolVersion": 1,
  "spaceId": "space-example",
  "epoch": "epoch-example",
  "device": {
    "deviceId": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "name": "工作电脑"
  },
  "records": [
    {
      "recordId": "fd3127c801e7b05afb5d900c6f091806b8e01e5f64a5b3ce70fe22fba89d5f67",
      "record": {
        "kind": "session",
        "sessionId": "thread-1",
        "forkedFromId": null,
        "createdAt": 1791504000000
      }
    },
    {
      "recordId": "ba432543859b5784bca4c5293c5c41afdb1ba4be71677028f0d664854620df5f",
      "record": {
        "kind": "usage",
        "sessionId": "thread-1",
        "timestampMs": 1791504000000,
        "model": "gpt-example",
        "inputTokens": 80,
        "cacheReadTokens": 20,
        "outputTokens": 10,
        "totalUsage": [100, 20, 10, 0, 110],
        "occurrence": 0
      }
    }
  ]
}
```

成功响应如下；重复提交整个请求也必须成功返回相同的确认集合。

```json
{
  "spaceId": "space-example",
  "epoch": "epoch-example",
  "acknowledgedIds": [
    "fd3127c801e7b05afb5d900c6f091806b8e01e5f64a5b3ce70fe22fba89d5f67",
    "ba432543859b5784bca4c5293c5c41afdb1ba4be71677028f0d664854620df5f"
  ]
}
```

`acknowledgedIds` 恰好包含本批所有 ID，每个一次，顺序不限，
包括之前已经存在的记录。不能只确认新插入的部分，也不能附带其他批次的 ID。
`records: []` 合法，用于登记设备或更新名称，成功时返回 `acknowledgedIds: []`。

客户端每批没有重复 ID。建议服务端对单批重复 ID 返回 400，
以免与确认集合的唯一性产生歧义；跨请求重传必须幂等成功。

### GET changes

路径为 `/api/v1/codex-usage/changes`，参数如下：

| 参数 | 要求 |
| --- | --- |
| `spaceId` | 必填，必须属于当前密钥授权的空间 |
| `epoch` | 必填，必须为该空间当前代次 |
| `limit` | 可选，整数 1～500，默认 500；当前客户端发送 500 |
| `cursor` | 可选，不透明字符串，非空且最多 4096 UTF-8 字节；省略表示从头读取 |

首次请求示意：

```http
GET /api/v1/codex-usage/changes?spaceId=space-example&epoch=epoch-example&limit=500
Authorization: Bearer <共享同步密钥>
Accept: application/json
```

以下为一页包含用量记录和设备信息的响应。`records` 的每项使用
`deviceId + item` 包装，`item` 才包含 `recordId + record`，不能把字段平铺。
完整首次下载还应包含此前上传的 session 记录，可以位于其他页。

```json
{
  "spaceId": "space-example",
  "epoch": "epoch-example",
  "records": [
    {
      "deviceId": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "item": {
        "recordId": "ba432543859b5784bca4c5293c5c41afdb1ba4be71677028f0d664854620df5f",
        "record": {
          "kind": "usage",
          "sessionId": "thread-1",
          "timestampMs": 1791504000000,
          "model": "gpt-example",
          "inputTokens": 80,
          "cacheReadTokens": 20,
          "outputTokens": 10,
          "totalUsage": [100, 20, 10, 0, 110],
          "occurrence": 0
        }
      }
    }
  ],
  "devices": [
    {"deviceId": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa", "name": "工作电脑"}
  ],
  "nextCursor": "opaque-checkpoint-token",
  "hasMore": false
}
```

示例游标仅为占位符，真实编码由服务端实现。后续请求通过 URL 编码原样回传游标。
即使没有任何变更，也必须返回两个空数组、非空 `nextCursor` 和 `hasMore: false`。
只有设备改名时可以返回空 `records`，不能因此丢弃设备变更。

下载必须包含当前设备自己的服务端记录。上传确认不代表客户端已下载它们，
不能据此过滤当前设备，也不能通过 push 响应推进下载游标。

## 持久化与原子上传

以下是建议的逻辑模型，表名不是协议的一部分。

| 表或实体 | 主键或唯一约束 | 保存内容 |
| --- | --- | --- |
| `spaces` | `space_id` | 持久 `epoch`、空间内已提交变更序号 |
| `sync_keys` | 密钥摘要或配置标识 | 授权空间、启用状态；不存于公开配置 |
| `devices` | `(space_id, device_id)` | 设备当前名称 |
| `records` | `(space_id, record_id)` | 不可变规范化记录及种类 |
| `record_sources` | `(space_id, device_id, record_id)` | 每条记录的全部采集来源 |
| `changes` | `(space_id, epoch, seq)` | 来源关系新增或设备信息变化的不可变快照 |

也可以把 records 与来源关系合并为一张表，但幂等键必须是
`(spaceId, deviceId, recordId)`。同一记录由 A 和 B 上传时，
两个来源都要进入变更流；不能仅以 `recordId` 去重后丢掉 B 的来源。

不要以 `sessionId` 作为不可变 session 记录的唯一键。
同一个会话的元信息修正可能形成新内容 ID，历史记录必须保留。
用量可先于 session 到达，子会话也可先于父会话到达；
不能用“父会话必须存在”或“用量会话必须先注册”的外键约束拒绝合法上传。

每次 push 按以下顺序处理：

1. 限制请求体大小，校验认证、协议版本、空间、代次、设备及完整记录列表。
   重算每条哈希，任何一条不合法都拒绝整批。
2. 开始数据库事务，锁定空间状态并再次核对当前 epoch，
   防止验证与提交之间发生数据重建。
3. 新增或更新设备名称，仅在确实变化时追加设备变更快照。
4. 插入尚不存在的记录与来源关系，仅对新增来源关系追加记录变更。
   内容和来源都相同的重传是成功的空操作。
5. 在同一事务内更新变更序号并持久提交，再返回整批确认集合。
   任何数据库失败都回滚设备、记录、来源、序号及变更流。

依赖数据库唯一约束和事务保证并发安全，不能只用进程内集合判重。
服务端提交后响应丢失时，客户端会重传；重传不得追加重复变更或累计用量。
正常重启后，已确认数据、幂等约束、代次和游标继续有效。

变更序号必须按可见的提交顺序推进。例如 T1 先取得序号 10 却未提交，
T2 的序号 11 先提交，下载游标就可能越过之后才出现的 10。
建议用空间行锁串行分配并提交该空间序号，锁持有到事务结束；
普通数据库自增序列本身不能消除这个问题。

## 固定上界与下载游标

游标对客户端是不透明的。建议采用持久化随机令牌，或携带服务端签名的编码数据。
服务端内部至少需要空间、epoch、当前位置、分页上界和游标类型。
内部序号不要经过 JavaScript 不安全整数转换；游标签名密钥须跨重启保留。
每次使用都核对认证空间、代次、位置范围及完整性，不能接受客户端任意修改的位置。

建议区分“分页游标”和“检查点游标”，流程如下：

1. 无游标：当前位置设为 0，读取该空间当前已提交的最大序号作为上界。
2. 检查点游标：从上轮检查点之后开始，重新取得当前已提交上界。
3. 分页游标：沿用其中的当前位置和固定上界，不能重新抬高上界。
4. 按序读取 `当前位置 < seq <= 上界` 的变更流连续前缀，
   分别放入 records 和 devices，保留各数组内的变更顺序。
5. 上界内还有未发送的变更时返回 `hasMore: true`，
   新分页游标指向本页最后一个已发送序号，并保留本轮上界。
6. 到达上界后返回 `hasMore: false` 和检查点游标。
   下轮使用该检查点时取得新的上界，才能持续接收后续增量。

例如第一轮固定上界为 120，翻页期间新增到 135：本轮必须在 120 结束，
不能追着新数据无限翻页；下一轮从 120 后读取至新的上界。
仅把旧上界永久编码进所有后续游标，会导致第一轮之后再也读不到新增数据。

分页还必须满足以下约束：

- 同时检查记录来源与设备变更的合计条数，以及整个响应的实际序列化字节数。
  字节数包括包装、字符串转义、空间信息、游标和所有设备信息。
  每页变更总数不得超过 limit（1～500，默认 500），不要求填满。
- 添加下一条后若超限，应留给下一页；游标不得越过这条尚未返回的变更。
  不能只查满 500 条后截断结果，却仍推进到查询末尾。
- `hasMore: true` 时至少一个数组非空，nextCursor 必须前进，
  不能重复本轮出现过的游标。最终空页可以返回原检查点。
- 设备改名也走同一条变更流，并使用变更发生时的设备信息快照。
  不能在旧页中连接 devices 当前值，把超过本轮上界的新名称提前返回。
- 不能因记录暂无设备名称、没有 session 元信息或祖先尚未上传而隐藏记录。
- 两个客户端从同一旧游标读取互不影响。服务端不能把读取当作消费或确认，
  不能为所有客户端共享一个不断前进的下载位置。

客户端会在同一 SQLite 事务中保存整页记录、设备信息和 nextCursor。
响应中断、校验失败或本地写入失败时，该页不提交，下次仍从原游标重读。
服务端需要支持这种重放，也必须让有效分页游标在正常重启后继续可用。

v1 建议保留完整变更流，不按设备最后同步时间淘汰历史。
如果之后实现压缩或过期，失效游标必须返回 409，并仍能从头重建完整存档；
不能悄悄从“当前最早还存在的位置”继续，造成无提示的数据缺口。

## 数据代次与失败恢复

服务端更换 epoch 后，旧 push 和 changes 返回 409。
客户端重新握手，清除该空间上传确认和下载游标，重新提交全部本机采集历史，
并从头下载。即使 epoch 没变化，无效游标返回 409 也触发重新确认和下载。
客户端当轮最多自动执行一次这样的恢复，持续返回 409 会进入失败退避。

服务端不能把所有客户端的下载缓存当作灾难恢复副本。
客户端只上传自身采集记录；某条记录的原采集设备已不在线时，
其他设备不会把下载到的副本重新上传。正式存储必须有独立的持久化与备份策略。

MAA 在同一空间的 epoch 变化后保留已有远端历史，再合并重新下载的数据。
因此更换 epoch 不等于远程删除，也不能用它实现服务端清空后让客户端同步清空。
不同 spaceId 则隔离缓存；不同服务器或密钥也使用独立本地同步配置空间。

客户端运行顺序为：采集全部本机历史、握手、分批 push、分页 changes。
保存配置、启动和计时器可以触发同步；同一进程内的并发触发会合并。
同步中切换配置会使旧请求的本地结果作废，但已经发出的请求仍可能在服务端提交。
服务端按每个请求携带的有效密钥和空间完成事务即可，不提供撤回请求接口。

### 错误响应

建议错误正文保持如下结构，不回显密钥、原始请求或内部堆栈。
客户端主要按 HTTP 状态分类，不直接向用户展示服务器的错误正文。

```json
{"code": "invalid_request", "message": "Invalid sync request"}
```

| HTTP | code | 使用场景与客户端行为 |
| --- | --- | --- |
| 400 | `invalid_request` | 字段、哈希或版本无效；暂停自动同步，等待配置修正 |
| 401 | `unauthorized` | 密钥缺少、无效或已重置；暂停自动同步并提示更新所有机器的密钥 |
| 403 | `forbidden` | 账户停用；暂停自动同步并提示联系管理员，启用后可手动重试 |
| 409 | `reset_required` | 空间、epoch 不一致，或游标无效、过期；重新握手并重放历史 |
| 413 | `payload_too_large` | 请求超过 1 MiB 或记录超过 500；暂停自动同步 |
| 429 | `rate_limited` | 触发限流，附 Retry-After；客户端按 v1 固定退避重试 |
| 5xx | `server_error` | 存储或服务暂时失败；退避后重试 |

网络错误、超时、429 和 5xx 使用 5／10／20／30 分钟退避，上限 30 分钟。
成功后恢复配置间隔，默认 5 分钟，其他选项为关闭自动同步和 15／30／60 分钟。
手动同步可以立即重试。服务端不能依赖客户端按 Retry-After 精确调度。
不要把数据库暂时不可用映射成 400，否则客户端会暂停自动同步。

## 统计与兼容边界

服务端原样分发验证通过的记录。谱系关系合并、累计计数器去重和来源集合
由客户端在完整关系图上完成，然后才筛选设备和时间。
父会话晚到时，客户端可能修正先前的规范事件及归属日期，服务端不预先按日期聚合。

费用使用查看机器的当前价格表计算，日期按查看机器的本地时区划分。
没有时间的记录计入合计，但不进入日或小时序列。服务器不把时间转换成本地日期，
也不把未知模型替换成服务端熟悉的模型。

v1 的字段、Token 口径、哈希、来源幂等键和删除语义固定。
新增记录种类、改变哈希或引入删除需要新协议版本和新接口路径，
不能只让 handshake 继续返回 1，然后改变后续报文含义。

## 验收场景

服务端测试使用隔离数据库、临时密钥和模拟记录，不读取真实 GPT 凭据或日志。
除字段单测外，还要通过真实 HTTP 入口验证存储事务、序列化和错误状态。
两个客户端必须使用不同设备 ID，不能复制同一个设备身份进行双机验证。

| 场景 | 必须得到的结果 |
| --- | --- |
| 空中心与无本机日志设备 | 握手成功；空列表上传及下载成功；游标有效且无死循环 |
| A 首次全量，B 下载 | 全部 session、usage 和设备信息完整到达 B |
| A 新增记录后再次同步 | B 从旧检查点取得增量；首次分页上界不会冻结所有未来同步 |
| 同批重传、两个请求同时重传 | 每个来源记录仅一份；确认始终完整；重复数据不新增变更 |
| 提交成功后连接断开 | A 重传成功；服务器没有重复记录或变更 |
| 一条错误哈希混入正常批次 | 全批拒绝，设备名称、记录、来源和序号均不部分提交 |
| 写入中途数据库报错 | 完整回滚并返回 5xx；恢复后重传成功 |
| 超过 500 条及大字段分页 | 请求超限返回 413；响应始终同时满足数量和 1 MiB 上限 |
| 分页期间持续上传 | 每轮在固定上界结束；下一轮读取新增数据，无遗漏 |
| 序号分配后延迟提交 | 并发下载不会跳过之后提交的较小序号 |
| 分页中断后重试、服务重启 | 旧游标可续传，重读同页不丢失或累加记录 |
| 只有设备改名 | 空记录页仍返回设备变更；重复相同名称不产生新变更 |
| 翻页期间再次改名 | 当前页不越过固定上界泄漏新名称；下一轮取得新名称 |
| A、B 上传同一条记录 | 保留两条来源关系；下载给两端；MAA 全部设备汇总仅计一次 |
| 分叉跨机器、祖先晚到 | 所有关系记录完整保留；客户端最终谱系统计与单机完整日志一致 |
| 无累计计数器的重复事件 | occurrence 不同的记录均保留，不合并真实重复明细 |
| 中文、引号、反斜杠和大整数 | 三个哈希向量一致；最大合法 Token 不丢精度；越界值拒绝 |
| 不同密钥与空间 | 数据隔离；错空间游标不能读取别的空间，不能绕过认证 |
| 同账户换钥 | 旧钥 401，新钥沿用空间、epoch 和历史；本机历史重传不重复计数 |
| 账户启停 | 停用 403，保留本机历史；启用后手动同步继续，成功后恢复自动同步 |
| 错误密钥、未知协议、未知字段 | 返回相应错误；客户端不把失败视为上传或下载成功 |
| 伪造或过期游标 | 返回 409；重新握手与全量重放可恢复，不静默跳过数据 |
| epoch 改变 | 旧 epoch 请求失败；本机历史重新确认；新游标可全量下载 |
| 本机缓存清理与原日志删除 | 服务器没有删除操作；缓存可下载恢复，已采集历史仍可查看 |
| 同步中修改服务器或密钥 | 已到达服务器的请求保持事务语义；客户端不提交过时结果 |

复制日志的最小断言可以使用本文示例：A 和 B 都采集同一 usage 时，
全设备总计仍为输入 80、缓存读取 20、输出 10；按 A 或 B 筛选都能看到该事件。
新增不同累计计数器的事件后总计才增加。父子分叉去重还需包含对应 session 记录。

客户端已有专项测试入口见[测试说明](../scripts/codex-sync-tests/README.md)。
这些测试中的模拟中心能说明客户端预期，但不能替代对新服务端的 HTTP 契约测试。
联调应覆盖主窗口与托盘的汇总一致性、设备筛选、离线展示和本地清理后恢复；
服务端 agent 可先交付 API 验收结果，再由可运行桌面应用的环境完成界面联调。

## 交付检查

- 三个接口和配置示例可在隔离环境启动，测试不依赖正式域名或真实用户数据。
- 数据库迁移包含来源唯一约束、事务和变更流索引，重启不丢记录或游标能力。
- 自动测试覆盖哈希向量、认证隔离、原子上传、丢失响应、并发序号和固定上界分页。
- 启动说明列出密钥与空间配置、持久数据库位置、HTTPS 入口和测试命令。
- 恢复说明写清何时更换 epoch，以及数据、游标密钥和配置如何备份与恢复。
- 配套 OpenAPI 与实际响应一致，说明采用的游标编码、失效策略和并发提交方案。
- 交付时列出已通过的测试与尚未完成的桌面联调，不把模拟中心测试当作正式服务验收。
