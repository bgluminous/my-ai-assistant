# GPT 用量同步协议 v1

本规范对应 MAA 客户端与中心服务的 v1 接口；JSON 结构见
[OpenAPI](gpt-usage-sync-v1.openapi.json)。规范中的「必须」为互通要求。
账户、密钥与分页边界已按 2026-10-12 的服务端交付说明对齐。

## 1. 范围与连接

- 仅同步 Codex 用量，会话关系用于去重，不提供会话恢复、账号同步或服务端删除接口。
- 基础地址可含路径前缀，客户端追加 `/api/v1/codex-usage/`。
  只接受 HTTPS；拒绝 URL 用户信息、查询参数、片段及 HTTP 重定向。
- 每个请求必须带 `Authorization: Bearer <key>` 和 JSON Accept 头。
  密钥由服务端管理员创建账户时生成，不是 OpenAI API Key 或 GPT 登录凭据；
  v1 无注册接口。同一账户的所有机器使用同一个密钥，各自保留独立设备 ID。
- 服务端将有效密钥映射到稳定的 `spaceId`。不同空间的数据和游标必须隔离。
  一个账户对应一个空间和一个当前有效密钥；账户启停及换钥不改变空间、epoch 或历史。
  spaceId、epoch 以握手为准，不从密钥推导，不要求用户填写账户 ID。
  密钥、Authorization、请求正文及游标不得写入访问日志。
- 服务端生成持久的 `epoch`。会让既有确认或游标失效的数据重建必须更换 epoch。
  `spaceId`、`epoch` 为 1～256 UTF-8 字节的非控制字符字符串。
- 单次请求和响应的未压缩 JSON 最大 1 MiB；上传记录最多 500 条。
  下载每页的记录来源与设备变更合计不超过 limit，limit 为 1～500，默认 500。
  服务端必须同时按字节和数量分页，不得截断 JSON 或单条记录。
- 本机请求超时 40 秒。客户端未配置地址和密钥时不发送同步请求。

## 2. 身份和记录

设备 ID 为本机随机生成的 128 位值，编码为 32 个小写十六进制字符，不来自硬件信息。
设备名称为 1～128 UTF-8 字节，不含控制字符，名称变化不改变设备身份。
备份不携带设备 ID，设备名称和采集目录仍使用目标机器原有值。

同步记录分两类，所有字段使用 camelCase：

| 类型      | 字段                                                                                                              |
| --------- | ----------------------------------------------------------------------------------------------------------------- |
| `session` | `sessionId`、`forkedFromId`、`createdAt`                                                                          |
| `usage`   | `sessionId`、`timestampMs`、`model`、`inputTokens`、`cacheReadTokens`、`outputTokens`、`totalUsage`、`occurrence` |

- 时间为 UTC Unix 毫秒整数，可为 null；范围为 `0..8210266876799999`，
  对齐 Chrono 0.4.45。未知时间计入合计，不进入日／小时序列。
- 会话 ID 使用原日志首条 session_meta 的 ID；无 ID 时使用持久的
  `legacy:<deviceId>:<随机文件ID>`，原路径只保存在本机。
- `forkedFromId` 可为 null。即使会话没有用量，也上传关系记录以连接多级分叉。
- 输入 Token **不含缓存命中部分**，等于原日志 input_tokens 减 cached_input_tokens，
  下限为零；另传缓存读取和输出 Token。输出已包含推理 Token，禁止再次累加推理值。
- `totalUsage` 可为 null，否则为原日志累计计数器数组：
  `[input_tokens,cached_input_tokens,output_tokens,reasoning_output_tokens,total_tokens]`。
- Token 均为非负整数，最大 `9007199254740991`；模型与会话 ID 最多 512 UTF-8 字节，
  非空且不含控制字符。父会话 ID 使用相同限制。
- 有累计计数器时 occurrence 必须为 0。没有累计值时，按单文件原顺序为完全相同的
  规范化用量内容从 0 开始编号，避免把旧日志中真实的重复明细合并。
- 模型未知用 `unknown`。零消耗的上下文压缩事件不采集。
- 不携带价格、聚合费用、对话正文、工具参数、工作目录、原日志路径或账号凭据。

### 2.1 记录 ID

`recordId` 是下列固定顺序 JSON 数组的 UTF-8 字节的 SHA-256 小写十六进制值：

```text
[1,"session",sessionId,forkedFromId,createdAt]
[1,"usage",sessionId,timestampMs,model,inputTokens,cacheReadTokens,outputTokens,totalUsage,occurrence]
```

JSON 无额外空白，整数使用十进制，不转义 `/` 和非 ASCII 字符。
字符串按标准 JSON 转义双引号和反斜杠。不存在的可空值必须编码为 null。
请求中的数字同样必须使用非负十进制整数原文，不接受小数、指数和负零。
字符串原样保留，不裁剪或做 Unicode 归一化；拒绝非法 UTF-8 和孤立代理项。
哈希不包含设备 ID，旧日志合成的 sessionId 除外。

记录包装如下，record 对象的键顺序不影响 ID：

```json
{
  "recordId": "ba432543859b5784bca4c5293c5c41afdb1ba4be71677028f0d664854620df5f",
  "record": {
    "kind": "usage",
    "sessionId": "thread-1",
    "timestampMs": 1791504000000,
    "model": "gpt-example",
    "inputTokens": 80,
    "cacheReadTokens": 20,
    "outputTokens": 10,
    "totalUsage": [100, 20, 10, 0, 110],
    "occurrence": 0
  }
}
```

服务端必须验证字段及哈希，以 `(spaceId,deviceId,recordId)` 唯一保存不可变记录。
相同记录重复提交是成功的空操作。内容校正产生新的内容 ID，统计时再去重。

跨语言校验向量（每个数组为完整一行 UTF-8 字节，无末尾换行）：

```text
[1,"session","thread-1",null,1791504000000]
SHA-256: fd3127c801e7b05afb5d900c6f091806b8e01e5f64a5b3ce70fe22fba89d5f67
[1,"usage","会话/\"1",null,"模型\\A",1,0,0,null,2]
SHA-256: 8301484be9dc31c5b241658355f3e68a5efde92ac2e716a158783cf1974dcb22
```

### 2.2 统计语义

先汇集全部设备的会话关系，再将用量按「谱系根＋累计计数器快照」合并。
缺少累计值时按 recordId 合并。同一规范事件保留全部来源设备的集合。
设备筛选根据此集合决定是否展示该事件，之后再按时间区间过滤。

规范事件按以下优先级选择：谱系深度较浅、会话创建时间较早、事件时间较早、
recordId 字典序、设备 ID 字典序；未知时间排最后。这样父日志晚到时可以修正分叉复制的时间。
缺少祖先时以最后一个已知父 ID 为根；引用环统一使用环内 ID 中的最小值，深度为零。
环外子节点仍归于该根，正常的多级分叉不截断。
关系记录冲突时优先非空值，父 ID 取字典序最小值，创建时间取最早值。

同一事件可能分别出现在多台设备视图，合并总计只计一次；设备分项不保证可直接相加。
无原始会话 ID 的旧日志只保证本机幂等，无法识别跨机器复制件。

## 3. 接口

### GET handshake

成功返回 HTTP 200：

```json
{"protocolVersion":1,"spaceId":"space-example","epoch":"epoch-example"}
```

测试连接只调用此接口，不保存配置、不上传明细。协议版本不为 1 时停止同步。

### POST push

Content-Type 为 application/json。即使没有新记录，也可以提交空列表以更新设备名称。

```json
{
  "protocolVersion": 1,
  "spaceId": "space-example",
  "epoch": "epoch-example",
  "device": {"deviceId":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","name":"工作电脑"},
  "records": []
}
```

服务端先验证完整请求、空间、epoch 和每条记录，再用单个事务提交整批。
成功返回 HTTP 200，acknowledgedIds 必须恰好包含本批所有 recordId，每个出现一次，
包括已存在的记录；顺序不限。客户端仅在核对全部确认后才保存本机上传确认。

```json
{"spaceId":"space-example","epoch":"epoch-example","acknowledgedIds":[]}
```

返回成功前必须完成持久化；请求失败或响应丢失后重发同一批不会产生重复用量。
服务端为每条新增记录及真正变化的设备信息分配空间内递增的变更序号，
重复记录和没有变化的设备名称不得产生新变更。

### GET changes

查询参数：`spaceId`、`epoch`、`limit`（客户端发送 500）、可选的 `cursor`。
无 cursor 表示从头读取；游标是不透明字符串，最长 4096 字节，客户端不得解析或修改。

```json
{
  "spaceId": "space-example",
  "epoch": "epoch-example",
  "records": [],
  "devices": [{"deviceId":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","name":"工作电脑"}],
  "nextCursor": "opaque-next-cursor",
  "hasMore": false
}
```

records 中每项是 `{"deviceId":"...","item":{"recordId":"...","record":{...}}}`。
客户端可能先收到记录、后收到设备信息，此时临时显示设备 ID 的短名。
下载包含当前设备自身来源；设备改名也是变更事件，与记录共享分页条数限制。

每轮查询首次请求时固定变更序号上界；中间游标包含该上界和当前位置，
后续页不得混入超过上界的变更。最后一页返回可从该上界继续增量读取的检查点游标。
必须同时返回 records 和 devices，不能因空用量页而跳过设备变更。
中间页必须有数据、游标必须前进；最终空页允许重复当前游标。
游标绑定空间和 epoch，无效游标返回 409；正常重启不使游标失效。
当前服务端游标没有常规过期时间，客户端仍仅将其视为不透明字符串。

客户端逐页验证记录，在一个 SQLite 事务中保存数据、设备信息和 nextCursor。
任一验证或写入失败时整页回滚。上传确认绝不能代替下载游标。

### 错误与重试

错误正文建议为 `{"code":"unauthorized","message":"..."}`，不得包含密钥。
客户端以状态码处理，不直接显示不可信服务端错误正文。

| HTTP      | code                     | 客户端行为                                             |
| --------- | ------------------------ | ------------------------------------------------------ |
| 400       | invalid_request          | 暂停自动同步，提示协议不符                             |
| 401       | unauthorized             | 密钥无效或已重置，暂停自动同步，更新所有机器的密钥     |
| 403       | forbidden                | 账户停用，暂停自动同步，联系管理员启用后手动重试       |
| 409       | reset_required           | 重新握手、重新确认本机历史并从头拉取，当轮最多重试一次 |
| 413       | payload_too_large        | 暂停自动同步，提示协议不符                             |
| 429       | rate_limited             | 服务端附 Retry-After；客户端按 v1 固定退避重试          |
| 5xx       | server_error             | 退避重试                                               |

网络、超时、429、5xx 使用 5／10／20／30 分钟退避，上限 30 分钟。
服务端不能依赖客户端按 Retry-After 精确调度；鉴权失败限流也可能返回 429。
正常自动间隔可设 5／15／30／60 分钟，关闭自动后只执行手动或配置保存触发的同步。
手动同步可立即重试。一次进程内只运行一轮同步，并发触发合并。
不兼容版本、畸形响应、无效记录或超限响应会暂停自动同步；修正配置解除暂停。

## 4. 客户端数据生命周期

- 原始数据在 `codex-usage.sqlite3` 持久保存；旧版聚合缓存不作为同步源，
  首次运行重新采集原日志。归档目录与活动目录均扫描，不受当前界面日期范围限制。
- 更换服务器或密钥切换本地命名空间。下载记录从不进入上传队列，
  新空间只上传本机采集历史。清空地址后停止同步，仅显示本机采集存档。
  同账户换钥也重新握手、全量同步，不能跨密钥复用确认状态；
  服务端保留历史与来源，通过幂等键避免重复计数。
- epoch 变化时清除该空间上传确认与游标，重新确认本机历史，保留已有远端历史。
  spaceId 变化时还必须隔离旧远端缓存，不能混入新空间。
- 配置或缓存变化使旧请求失效；已经送出的 HTTP 请求可能完成，但不能再更新旧游标。
- 删除原日志不删除存档。按设备清理只删除当前 MAA 已同步的用量缓存，
  会话关系与未上传记录保留；服务器、其他机器和原日志不受影响。
  清理后界面只重读存档，下次扫描或同步可以恢复历史，不产生全局删除标记。
- 密钥本地保存使用应用已有加密封装，仅防止直接读取，不能防御反编译。
  连接配置随备份携带，设备身份、名称、采集路径、数据库和游标不随备份复制。
  旧备份缺少同步字段时保留当前同步配置。

## 5. 服务端验收

必须覆盖双客户端全量／增量互通、复制日志幂等、响应丢失重试、固定上界分页、
设备改名、空间隔离、epoch 变化、无效游标、批次原子失败、超限记录及未知协议版本。
服务端不需要计算费用和合并谱系，只需可靠保存、验证和转发规范化记录。
客户端测试替身不是可部署服务，不提供生产存储、运维或密钥管理实现。

## 6. 兼容策略

v1 的记录字段、哈希顺序、Token 口径和幂等键固定，不得在原接口上变更含义。
记录及设备对象拒绝未知字段；握手、确认和分页响应允许增加不影响现有语义的字段。
新增记录种类、修改哈希或删除语义需要新协议版本和接口路径。
客户端遇到非 v1 版本暂停自动同步，保留存档与未上传记录，不能降级后继续写入。

旧版 MAA 设置没有同步配置时默认为空地址、空密钥、5 分钟间隔。
旧备份缺少该字段时保留目标机器的配置；包含配置时只迁移连接与间隔。
客户端专项测试入口和隔离范围见 [测试说明](../scripts/codex-sync-tests/README.md)。
